# Android-модель и локальный сервер

Модель `.tflite` работает на телефоне. Backend не загружает её и не требует интернета для этих операций. Телефон обращается к локальному серверу по Wi-Fi. Без связи с сервером очередь осмотров и кеш карточек должен обеспечить Android; сервер принимает накопленные осмотры с исходным временем съёмки и ключом повтора.

## Контракт модели

Администратор входит в кабинет и вызывает `POST /api/v1/mobile-models` через Swagger. Нужны SHA-256 файла, версия, порог и полный список `labels` по порядку от нуля. Для каждой метки задаются `class_id`, `name`, `kind` (`DEFECT`, `NORMAL`, `UNKNOWN`) и необязательный `defect_type_id` из серверного справочника. Метка NORMAL не является неисправностью. Неизвестные классы должны быть явно описаны как UNKNOWN. Существующий контракт по SHA не перезаписывается.

Профиль не регистрируется автоматически по сообщениям команды. У присланного `best_float16.tflite` SHA-256 `0c6ce9b3990dcfd9607a3bab073c66a42d4db882ae111676960dd59e6cf7b774`, вход `[1,640,640,3]` FLOAT32, выход `[1,17,8400]`: финальная операция объединяет 4 координаты и 13 каналов оценок. Перед включением нужен подтверждённый список классов: в переписке их было 12. Порог уверенности не означает тяжесть повреждения.

## QR и карточки

QR содержит точный `inventory_number`, например `pump_001`, а не произвольный внешний URL.

- `GET /api/v1/equipment/resolve?code=pump_001` — разрешение QR в числовой ID и расширенную карточку.
- `GET /api/v1/equipment/{id}/card` — та же карточка по ID: паспорт, компоненты, характеристики и ресурс.
- Старый `GET /api/v1/equipment/{id}` остаётся совместимым.

Сотруднику доступны только записи своего цеха. Bearer-токен получается через `POST /api/v1/auth/token` с JSON `login/password`.

## Осмотр с телефона

`POST /api/v1/inspections/mobile`, `Authorization: Bearer <token>`, `Idempotency-Key: <UUID>`:

```json
{
  "equipment_id": 1,
  "component_id": 2,
  "source": "CAMERA",
  "captured_at": "2026-11-13T09:00:00Z",
  "model_sha256": "0c6ce9b3990dcfd9607a3bab073c66a42d4db882ae111676960dd59e6cf7b774",
  "image": {"width": 1280, "height": 720},
  "defects": [{"class_id": 7, "confidence": 0.68, "box": [0.1, 0.2, 0.4, 0.6]}],
  "telemetry": []
}
```

ID и class_id в примере иллюстративные. `component_id` и `box` можно опустить. Имена классов и рекомендации клиент не задаёт. Все находки сохраняются, `accepted` показывает прохождение порога строго `confidence > threshold`. Известный дефект даёт предварительный WARNING независимо от уверенности; NORMAL, UNKNOWN и отсутствие находок дают UNKNOWN, а не подтверждение исправности.

Входные рамки — **[xmin, ymin, xmax, ymax] от 0 до 1**, относительно исходного кадра после коррекции поворота. Android самостоятельно снимает padding/масштаб letterbox 640x640, применяет NMS и переносит координаты к исходному кадру. Поле `detections[].box` в ответе остаётся нормализованным, верхний `box` — пиксельная рамка основной находки для совместимости с прежним API. Преобразование и скорость модели на телефоне сервер не подтверждает.

Ответ 201 содержит `inspection_id`, `photo_id: null`, серверное `created_at`, отдельное `captured_at`, список находок, SHA/версию модели, источник MODEL и место анализа ANDROID. Повтор с тем же ключом и содержимым возвращает исходный ответ; изменение запроса с тем же ключом — 409. Сохраняйте UUID при восстановлении связи. Сервер проверяет доступ, включая компонент, и не принимает время съёмки без часового пояса или более чем на пять минут в будущем.

Фото прикрепляется отдельно: `POST /api/v1/inspections/{id}/photo`, multipart с одним `image`. Только автор осмотра, JPEG/PNG до 10 МиБ и 20 млн пикселей. Размеры после EXIF должны совпасть с `image` осмотра. Повтор идентичного нормализованного снимка допустим; замена другим — 409. После загрузки GET осмотра и история возвращают актуальный `photo_id`, но повтор первоначального POST сохраняет свой исходный ответ с null. Чтение незагруженного фото — 404.

Старые маршруты `/inspections` и `/inspections/preview` сохраняют контракт с фотографией и серверным анализом. Они остаются выключенными без явного `ANALYSIS_MODE=mock`; новый мобильный маршрут от этого параметра не зависит.

## Компоненты, ресурс и работы

Администратор создаёт компонент через `POST /api/v1/equipment/{id}/components`. Нормы: `lifetime_days`, `lifetime_hours`, `lifetime_cycles`, `service_interval_hours`. Исходные данные: `installed_on`, `operating_hours`, `operating_cycles`, `last_service_hours`. Отсутствующие сведения оставляйте null. `specifications` — список параметров с `name`, `value`, `unit` и необязательными `minimum/maximum`.

В карточке ресурс вычисляется отдельно в днях, часах и циклах. Остаток — максимум из нуля и разности нормы и известной наработки. DUE означает достижение известного норматива, APPROACHING — остаток не более 10%; этот порог относится к демо-оценке ресурса. Нет исходных данных — INSUFFICIENT_DATA. Нормативный расчёт не является прогнозом физического отказа и не выводится из уверенности CV. Для интервала ТО нужны текущая наработка и наработка последнего обслуживания.

Мастер, инженер или администратор записывает работы через `POST /api/v1/components/{id}/work` с Idempotency-Key. Поля: `action` (`INSPECTED`, `SERVICED`, `REPLACED`, `READINGS`), `occurred_at`, `expected_revision` из карточки, непустой `comment`, необязательные показания наработки. После замены наработка нового компонента начинается с нуля. История хранит состояния до и после, автора и время получения. Устаревшая revision — 409; повтор ранее принятого действия воспроизводит его ответ. Наработка без замены не уменьшается; события, меняющие состояние, должны идти хронологически. `GET /api/v1/components/{id}/work?limit=20&offset=0` читает историю. Запись обслуживания не закрывает проблему автоматически — прежняя инженерная проверка и закрытие сохраняются.

## Показания датчиков и границы готовности

В `telemetry` принимаются значения `name`, `value`, `unit`, `measured_at` с часовым поясом, `source` (`SENSOR`, `MANUAL`, `DEMO`). Они хранятся как CLIENT_REPORTED. Нейросеть камеры не измеряет ток, давление, температуру или вибрацию. Автоматические диагнозы «кавитация», «расцентровка», «смазка», OCR приборов и поиск кожуха этим изменением не реализованы. Для них нужны согласованные источники, нормы, правила и модели. Зафиксированные демозначения должны иметь source=DEMO.

## Локальный запуск

### Android из `mobile/`

Быстрый запуск для участников описан в [README](../README.md): `go run deploy/local/main.go` одновременно начинает Docker-сборку APK и запуск сайта/API, затем автоматически вызывает локальную подготовку насоса, сотрудников и `demo_admin`. Отдельные пароли генерируются один раз в `.env.local` и выводятся в терминал. Команда `bootstrap-local` принимает их через JSON stdin, не через argv, и разрешена только при `LOCAL_DEMO_ENABLED=true`; этот флаг включён только в `compose.local.yaml`. Повтор проверяет существующие учётные записи и не меняет их пароли.

На сайте состояние APK берётся из локального `GET /api/v1/android-build`. Пока APK собирается или сборка завершилась ошибкой, старый файл не предлагается для скачивания; после публикации готового файла кнопка появляется автоматически. Мобильные исходники и сам APK проверяются по SHA-256: неизменившийся артефакт используется без Docker-сборки. BuildKit сохраняет Android SDK в слоях, а Gradle, конфигурацию и ключ debug-подписи — в кешах. APK публикуется атомарно, частичный файл не отдаётся. `--skip-apk` явно использует прежний APK, `--setup-only` завершает подготовку и выходит после готовности сборки.

Для автоматического определения IP запустите из корня `go run deploy/local/main.go` и оставьте команду работающей. Она выберет частный IPv4 интерфейса, создаст `.env.local` с отдельными случайными паролями при отсутствии файла и запустит Compose. На ноутбуке с несколькими сетями укажите `--host 192.168.1.50`. Команда отвечает на поиск Android по UDP 51020 только пока API отвечает на healthz. При Ctrl+C поиск завершается, контейнеры продолжают работать. Повтор запуска обновляет привязку порта к текущему IP без удаления данных.

Экран входа автоматически ищет сервер в Wi-Fi; доступна кнопка повторного поиска. Редактируемого поля IP нет: вход становится доступен после обнаружения сервера. Поиск привязан к Wi-Fi через Android Network, временно удерживает MulticastLock, не передаёт пароль или токен и проверяет nonce и совпадение адреса UDP-ответа с отправителем. Если broadcast недоступен, приложение проверяет известный адрес в текущей Wi-Fi-подсети, затем ограниченно ищет наш HTTP-сервис на порту 8001 в текущих /24-подсетях. Проверка `/mobile-server` включена только в локальной установке и возвращает идентификатор Industrial Vision и путь API. Уже сохранённые токены на новый адрес не пересылаются автоматически. Это обнаружение, а не криптографическая проверка подлинности сервера: используйте доверенную локальную сеть. Android 17 запрашивает разрешение доступа к локальной сети.

Вход получает Bearer-токен, имя, роль и цех с сервера; сохранённый токен проверяется через `/me`. Список оборудования, поиск по точному инвентарному номеру, карточка компонентов и последние 20 осмотров загружаются через локальный API. Телефону нужны доступ к LAN-IP и порту TCP 8001; для быстрого поиска — UDP 51020. Одной Wi-Fi-сети недостаточно, если роутер изолирует клиентов. Экран входа прокручивается и учитывает клавиатуру и системные панели; пароль скрыт по умолчанию, доступна кнопка «Показать / Скрыть».

Токен хранится через Android Keystore. Модель находится в `ai/models/best_float16.tflite`; Gradle включает этот каталог в assets APK, Docker собирает из корня репозитория с отдельным `.dockerignore`. SHA-256 модели включён в ключ кеша APK. На телефоне CameraX передаёт кадры в отдельный поток, TFLite получает RGB FLOAT32 640×640 с letterbox 114/255. Из выхода `[1,17,8400]` обрабатываются все 13 классов; координаты в пикселях входа восстанавливаются к исходному кадру, повороту и PreviewView через CameraX CoordinateTransform. Применяются строгий порог >0,4 и class-aware NMS 0,45. Класс 5 не является дефектом; класс 12 пока отображается как неизвестный. Пустой список находок не означает исправность, уверенность не определяет тяжесть. Анализ ограничен по частоте и прекращается при выходе с камеры; интерпретатор закрывается на том же потоке.

Команда ниже создаёт один условный насос `pump_demo_001`, три компонента и сотрудников `pump_worker` / `pump_engineer`. Она работает при `ANALYSIS_MODE=disabled`, спрашивает пароль, не генерирует осмотры и не регистрирует неподтверждённую модель. Повтор не сбрасывает накопленную наработку и не меняет пароль. При обычном старте демоданные автоматически не загружаются.

```bash
docker compose --env-file .env.local -p iv-local -f compose.local.yaml exec backend python -m app.manage seed-pump-demo
```

Для сборки нужны Android SDK 37.0, JDK по `mobile/gradle/gradle-daemon-jvm.properties` и доступ к репозиториям зависимостей при первом запуске. Из корня:

```bash
sh mobile/gradlew -p mobile :app:assembleDebug :app:testDebugUnitTest --max-workers=4
```

APK: `mobile/app/build/outputs/apk/debug/app-debug.apk`. После входа откройте камеру: анализ выполняется на телефоне, результаты рисуются поверх видеопотока. Кнопка «Пауза» останавливает обработку; карточки и история доступны через «Оборудование». Автоматическая отправка новых CV-осмотров в историю на этом этапе не подключена. Для демонстрации откройте на ноутбуке `/industrial-vision/cv-example` и наведите телефон на экран. Загрузка фото в приложение не используется. Пример — крупный план из демонстрационного изображения Qwen, предоставленного организаторами; исходник: https://disk.yandex.ru/d/CaiCoW791_PlJA, раздел «Насосные агрегаты», файл «2c510abd88b648efb8841d297d432aee.png». Полный исходник с watermark сохранён в `ai/demo/rust-pump-full.png` и доступен со страницы примера. Размер крупного плана — 1120×850, полного изображения — 2704×1536. Крупный план помогает распознаванию; на общих планах возможны пропуски.

В локальной сборке фронта на главной странице есть кнопка «Скачать APK». Прямая ссылка: `http://<LAN-IP>:8001/industrial-vision/android.apk`. Compose монтирует каталог готового APK только для чтения; новая Android-сборка становится доступна без пересборки backend. Маршрут включается только при `ANDROID_APK_PATH`, а кнопка — аргументом сборки `VITE_ANDROID_APK_URL`; production по умолчанию их не включает. Файл выдаётся как attachment с типом Android package. Отсутствующий APK даёт 404. Проверены сборка TypeScript/Vite, наличие кнопки в локальных JS и полное совпадение SHA-256 скачанного файла с APK.

`compose.local.yaml` запускает приложение и PostgreSQL без публичного Traefik и внешнего хранилища. БД подключена только к внутренней сети `data`; backend подключён к `data` и отдельной сети `local`, позволяющей опубликовать HTTP-порт для телефона. Образы и frontend должны быть собраны заранее при доступном интернете. В рабочем запуске сетевые загрузки не нужны.

```bash
docker compose -f compose.local.yaml build
docker compose -f compose.local.yaml up -d
docker compose -f compose.local.yaml exec backend python -m app.manage create-admin
```

До запуска задайте разные `IV_LOCAL_DB_PASSWORD` (приложение) и `IV_LOCAL_ADMIN_PASSWORD` (владелец PostgreSQL) в закрытом окружении или `.env`. Для пароля приложения используйте URL-безопасную случайную строку, например hex. Backend работает от отдельной роли iv_app без прав суперпользователя; SQL инициализации выполняется только при создании нового volume. Для телефона задайте `IV_LOCAL_BIND` равным LAN-IP сервера, а `IV_LOCAL_ORIGIN` — `http://<LAN-IP>:8001`. API: `http://<LAN-IP>:8001/industrial-vision/api/v1/`, кабинет: `http://<LAN-IP>:8001/industrial-vision/`. Префикс сохранён, поскольку frontend собран с этим адресом. По умолчанию порт доступен только на 127.0.0.1. Compose предназначен для HTTP-демо в изолированной LAN; для HTTPS используются локальный TLS-прокси и Secure-cookie. Рабочий production Compose не изменён. Обе установки требуют резервных копий БД и фотографий.

## Миграции

Схема сведена в один файл начальной миграции. Переход с исторических 0001–0005 выполняется без очистки данных, под существующей advisory-блокировкой и в транзакции; неизвестная версия или неполная историческая схема не помечается как успешно обновлённая. Проверяются новая БД, обновление всех старых ревизий и повторный запуск. Удалять volumes или вручную очищать alembic_version не требуется.
