# Industrial Vision — запуск через Docker

Локальный сервер, веб-кабинет и Android-приложение для осмотра оборудования. На компьютере нужны **Git и запущенный Docker с Compose v2 или новее**. Go, Python, Java, Android Studio и Android SDK устанавливать не нужно: зависимости работают внутри контейнеров.

## Подготовка компьютера

- **Windows 10/11:** Docker Desktop с WSL 2, режим Linux containers. Команды можно выполнять в PowerShell.
- **macOS:** Docker Desktop. На Apple Silicon сборщик Android работает через эмуляцию amd64 и может быть медленнее.
- **Linux:** Docker Engine, Compose plugin и доступ пользователя к Docker.

Перед запуском откройте Docker Desktop и дождитесь готовности движка. На Linux запустите службу Docker. Проверьте:

```bash
docker info
docker compose version
```

Первая сборка требует интернета для загрузки образов и зависимостей. После подготовки сайт, API и модель работают в локальной сети без интернета. Здесь проверяется Linux; Windows и macOS требуют отдельной проверки на этих системах.

## Скачать и запустить

```bash
git clone -b feat/complete-mvp https://github.com/TeamLeader-KS/Intelligent_System_AR.git
cd Intelligent_System_AR
docker compose up -d
```

Если проект уже скачан, выполните из его корня только:

```bash
docker compose up -d
```

При первом запуске Compose сам собирает недостающие образы. Контейнеры создают случайные пароли, PostgreSQL, схему базы, демонасос и пользователей. Сайт и API запускаются отдельно от фоновой загрузки Android SDK, сборки APK и подготовки серверной визуальной модели. Завершение команды не означает, что APK и серверный ИИ уже готовы. Первичная загрузка весов Qwen занимает около 1,93 ГБ; проверенные веса сохраняются в Docker volume.

Откройте на компьютере **http://localhost:8001/industrial-vision/**. На странице появится статус «APK собирается», затем кнопка скачивания. Если сборка не удалась, сайт остаётся доступен.

## Логины и пароли

```bash
docker compose logs bootstrap
```

В журнале подготовки будут:

```text
Администратор: demo_admin / <пароль администратора>
Android: pump_worker или pump_engineer / <пароль сотрудников>
```

Для сайта используйте администратора, для Android — сотрудника. Пароли автоматически сохраняются в Docker volume `secrets`. При повторном запуске они сохраняются; существующие аккаунты и наработка не сбрасываются. Журнал содержит пароли — не публикуйте его целиком.

## APK и телефон

1. Подключите телефон к Wi-Fi роутера, к которому подключён компьютер. Компьютер может быть подключён кабелем; гостевая сеть с изоляцией устройств не подходит.
2. Узнайте IPv4 компьютера (Ethernet при подключении кабелем, Wi-Fi при беспроводном подключении): `ipconfig` в Windows, настройки сети в macOS или `ip -4 addr` в Linux.
3. Откройте на телефоне `http://<IP компьютера>:8001/industrial-vision/`.
4. Дождитесь кнопки «Скачать APK», установите приложение и разрешите камеру и доступ к локальной сети, если система спросит.
5. Приложение ищет сервер через HTTP в Wi-Fi-подсети. Если сервер не найден, введите в поле «Адрес сервера» `http://<IP компьютера>:8001` или полную ссылку `/industrial-vision/api/v1/`, затем логин и пароль. Сохранённый адрес проверяется при следующем поиске независимо от подсети телефона. Отдельную программу на компьютере держать открытой не нужно. Войдите как `pump_worker`.
6. Откройте на ноутбуке ссылку «QR и шильдик для камеры»: QR содержит `pump_demo_001`, заводской номер — `DEMO-PUMP-2026-001`. В приложении используйте QR или «Считать шильдик» и подтвердите точный номер.
7. Выберите компонент. Для демонстрации откройте на ноутбуке «Пример насоса для камеры», наведите телефон на крупный план и нажмите сохранение осмотра. Сохраняется текущий результат и снимок живой камеры; загрузки фотографии из галереи нет.
8. Для регистрации проверки, обслуживания, замены и пуска/останова войдите как `pump_engineer`. Рабочему доступно сохранение осмотра. История и выгрузка PDF/Excel доступны в карточке.
9. Если сеть пропала при отправке, операция останется в локальной очереди. После восстановления связи повторите отправку: UUID и снимок сохраняются, дубли не создаются.

Разрешите входящий TCP 8001 в брандмауэре для частной сети. VPN, гостевой Wi-Fi и изоляция устройств могут мешать подключению. Проверка: `http://<IP компьютера>:8001/healthz` должна вернуть `{"status":"ok"}`. Автопоиск Android рассчитан на порт 8001 и текущую /24-подсеть; в других сетях он может не найти сервер.

Кабинет администратора по умолчанию настроен на `http://localhost:8001`. Скачивание APK и вход сотрудника с телефона доступны по LAN-IP. Если нужен **веб-кабинет администратора по LAN-IP**, создайте `.env` рядом с `compose.yaml`:

```dotenv
IV_LOCAL_ORIGIN=http://192.168.1.50:8001
```

Укажите свой IP и повторите `docker compose up -d`. После этого открывайте кабинет именно по указанному адресу.

## Повторный запуск, обновление и логи

```bash
# Запустить снова с сохранёнными данными и кешем:
docker compose up -d

# После получения новых исходников пересобрать образы:
git pull --ff-only
docker compose up -d --build

# Статус контейнеров:
docker compose ps -a

# Прогресс APK:
docker compose logs -f apk

# Ошибки API и подготовки пользователей:
docker compose logs backend bootstrap setup

# Подготовка и работа экспериментального серверного ИИ:
docker compose logs vision-prepare vision

# Остановить, сохранив данные:
docker compose stop
```

SDK, Gradle, ключ тестовой подписи, база, фотографии, APK и серверные веса сохраняются в Docker volumes. Если исходники Android, модель и файл APK не менялись, сборщик повторно использует готовый APK. После обновления мобильного кода выполните `docker compose up -d --build`: команда обновит образ сборщика.

Не удаляйте volumes, если нужны данные и пароли. `docker compose down -v` удаляет и базу, и пароли, и кеши. Старый запуск через Go использует отдельный проект `iv-local`; перед переходом остановите его, чтобы освободить порт 8001. Его база не переносится в новую демонстрационную установку автоматически.

## Makefile — по желанию

Если установлен Make, доступны короткие команды. Для основного запуска Make не требуется.

```bash
make up           # docker compose up -d
make credentials  # логины и пароли
make logs         # логи API, APK и подготовки
make stop         # остановить контейнеры
```

## Что работает

Базовый сценарий использует условный насос `pump_demo_001`, три компонента, параметры и начальную наработку, явно отмеченные как **ДЕМО**. Они не получены от реальных датчиков. Фиктивные осмотры не создаются. Карточки демонстрационной галереи и подготовленные записи из документов организаторов имеют разные источники; фотографии не подтверждают паспортные параметры агрегата.

Работают роли и авторизация, доступ по цехам, карточки, история, серверный приём результатов модели и учёт обслуживания. Модель `ai/models/best_float16.tflite` встраивается в APK и распознаёт дефекты живой камерой на телефоне. Порог строго выше 0,4; «Без коррозии» исключается из дефектов, неподтверждённый 13-й класс отображается как неизвестный. Отсутствие рамок не подтверждает исправность.

Осмотр сохраняется **по кнопке**, вместе с кадром и выбранным компонентом. QR читается встроенным ZXing, латинский шильдик — встроенной OCR-моделью ML Kit; при первом использовании скачивать модель не нужно. Тип узла текущая TFLite сама не определяет: привязка к компоненту выполняется инженером. Отдельный серверный режим Qwen предлагает типы и привязки видимых узлов, но они также требуют подтверждения.

В кабинете раздел «Осмотры и обслуживание» показывает карточки, нормы, историю, работы и диагностические сценарии. Состояние RUNNING увеличивает моточасы по времени сервера, STOPPED — нет. При замене счётчик нового компонента начинается с нуля; обслуживание работающего компонента требует его остановки. Доступны PDF и XLSX.

## Готовые данные для демонстрации

При запуске автоматически создаются:

- насос `pump_demo_001`, заводской номер `DEMO-PUMP-2026-001`, три компонента;
- сотрудники `pump_worker` / `pump_engineer` и администратор `demo_admin`;
- примеры ручной проверки компонентов, явно помеченные как синтетические;
- нормативы и уставки, принятые командой исключительно для демо;
- контракт встроенной модели: 12 известных меток и неизвестный класс 12.

Во вкладке «Осмотры и обслуживание» выберите подшипниковый узел, загрузите сценарии и проверьте кавитацию, смазку, расцентровку, утечку, крепления, масло, токи, давление или защитный кожух. Сценарии не запускают CV и не сохраняются как реальные осмотры. Показания имеют источник DEMO, визуальные замечания — MANUAL. Для ТО выполните явную запись работ; данные пользователя при следующем старте не сбрасываются.

В [галерее примеров](ai/demo/pumps/README.md) подготовлены **9 изображений похожих горизонтальных центробежных насосов и отдельных узлов: 3 реальных фото и 6 синтетических примеров**. Есть коррозия, капли у уплотнения, выступающая шпилька, открытая муфта без кожуха и уровень жидкости ниже MIN. У каждого примера отдельный QR и демонстрационный номер `pump_demo_001`–`pump_demo_009`; шильдик поверх изображения — демонстрационная привязка. Эти изображения не образуют независимый размеченный тест: затяжка болтов, внутренний износ и фактическая исправность по ним не подтверждаются.

## Реальные документы и справочные базы

[Комплект организаторов](data/organizers/README.md) содержит инвентарь **84 исходных файлов, около 186 МБ**: паспорта, инструкции, таблицы вибрации и температуры, описания дефектов и изображения. Сохранены пути источников, размеры и SHA256. Из 24 PDF извлечён текст 268 страниц; 210 страниц были сканами и прошли OCR. **Все 268 страниц не прошли полную ручную техническую проверку**; уверенность OCR не подтверждает правильность числа или норматива.

Для импорта подготовлены **9 структурированных записей оборудования и семейств**: четыре паспортных AMS PCP60S12/3, каталоги FCR и HF, две позиции Wilo и семейство из руководства Wilo. Это отдельный набор от девяти демонстрационных фотографий. Каталожное семейство не считается конкретным установленным агрегатом. Исходные факты имеют ссылки на файл и страницу; неподтверждённые сведения сохраняются с ограничениями.

Две базы содержат **по 500 строк, всего 1000 справочных записей**. Это исторические примеры организаторов, а не текущие показания подключённых датчиков. Совпадение времени и оборотов в таблицах не подтверждает, что они сняты с одного физического насоса. Колонка «Диагноз» сохраняется как авторская метка источника; её независимая эталонность не подтверждена. Эти строки не превращаются автоматически в реальные осмотры или фактические моточасы оборудования.

Винтовой AMS с мотором 1460 об/мин и редуктором отделён от центробежных справочных рядов примерно 2950 об/мин. Ресурс и регламенты одной конструкции не переносятся на другую. Производственная наработка должна иметь подтверждённый источник; начальные демочасы и время состояния RUNNING в прототипе не заменяют историю реального предприятия.

При локальном запуске bootstrap автоматически импортирует подготовленные паспортные факты и две таблицы в БД. Повторный импорт сохраняет наработку, установку и историю обслуживания. В кабинете раскройте «Паспортные сведения» у карточки `ORG-AMS-PCP-1`: там есть происхождение, страницы и статус проверки фактов. Это справочные карточки, а не подключённое к датчикам оборудование.

Оригиналы `data/organizers/raw/` исключены из Git. После клонирования восстановите их загрузчиком по [инструкции комплекта](data/organizers/README.md): нужны только Docker и интернет на этапе подготовки, скачанные файлы проверяются по размеру и SHA256, готовые пропускаются. Без оригиналов паспортные факты и таблицы доступны, а скачивание PDF недоступно. Перед выдачей оригинала API проверяет его SHA256. Открытая лицензия на весь комплект не указана.

## Модель и ограничения

В прототипе два независимых варианта анализа:

| Вариант | Назначение и ограничения |
|---|---|
| Android, `best_float16.tflite` | Локальная модель визуальных признаков коррозии. Кадры обрабатываются на телефоне без обращения к серверной нейросети; качество на целевых насосах и нагрузка конкретного телефона требуют проверки. |
| Локальный сервер, `qwen3-vl:2b-instruct` через Ollama | Экспериментальная универсальная визуальная модель: предполагаемые узлы и видимые признаки. В текущих CPU-прогонах ответ занимал примерно **25–50 секунд**; это не анализ видеопотока в реальном времени и не гарантия задержки на другом ПК. Есть пропуски и ошибочные находки; качество по каждому типу дефекта не подтверждено. |

Серверная модель работает на компьютере в локальной сети после подготовки весов. Ошибка, таймаут или отсутствие находок не означают исправность. Привязка узла — предложение модели, числовая достоверность серверных выводов не заявляется. Внутренний износ, кавитация, фактическая затяжка крепежа, температура и ток не измеряются по одному RGB-кадру.

Рабочая TFLite Софии остаётся исходной. [Подготовка данных и обучение](ai/training/README.md) содержит воспроизводимый процесс; [карточка экспериментального кандидата](ai/candidates/spiderbot-cpu-finetune/MODEL_CARD.md) — результаты реального CPU-дообучения другой открытой базы. Кандидат не установлен в APK: качество на контрольной выборке оказалось недостаточным. Это не подтверждённое улучшение модели насосов.

Обязательна проверка на реальном телефоне: чтение вашей таблички, геометрия рамок, скорость, нагрев и весь сценарий без интернета. Автоматическое распознавание типов узлов и подтверждённое качество на реальных насосах остаются открытыми пунктами; не заявляйте 100% выполнения ТЗ по одной успешной сборке.
